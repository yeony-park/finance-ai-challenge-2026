> 규약: `docs/worklog/README.md` 4섹션(결정과 근거/트레이드오프/검증 영향/알려진 한계).
> 배경: 2026-09-07 00:15~03:00 KST 배포 전 최종 점검. 한우 9호 청약(9/8 10:00~9/22 16:00)이 심사 기간(9/7~9/11)에 시작되므로 "라이브"가 실제로 무엇을 갱신하는지 확인했다.

## 작업 1 — 한우 상품 상세 정적 페이지 재생성 주기 (2026-09-07)

**결정과 근거** — `/cattle/products/[id]`는 `generateStaticParams`+`dynamicParams=false`의 정적 페이지이고, 청약 단계 배지는 `buildOfferSchedule(offerEntry, new Date())`로 렌더 시점에 계산한다. 재검증 주기가 없어 배포 시각의 단계가 그대로 굳는다(로컬 프로덕션 빌드 실측: 9호 상세가 "청약 · 예정"으로 고정). `export const revalidate = 600`을 추가해 Vercel이 10분 단위로 백그라운드 재생성하게 했다. `/cattle` 목록은 `searchParams`를 읽는 동적 페이지라 이미 요청마다 계산된다.

**트레이드오프** — 대안 ① `force-dynamic`: 매 요청 함수 실행으로 TTFB·비용 증가. ② 클라이언트에서 단계 계산: 하이드레이션 불일치 위험과 컴포넌트 구조 변경. ③ 9/8 10:00 이후 수동 재배포: 사람 의존. ISR은 한 줄 변경이며 첫 요청은 stale을 주고 뒤에서 갱신하므로 최대 10분 지연을 지불한다. 한돈 상세는 전 회차 종료, 부동산 상세는 고정 라벨이라 적용하지 않았다.

**검증 영향** — 빌드 산출물에서 해당 라우트가 ISR로 표시되는지, 배포 후 9/8 10:10 이후 상세 페이지가 "청약 진행 중"으로 바뀌는지 확인한다. 기존 라우트 정합성 테스트(`category-detail-consistency.test.ts`)는 영향 없음.

**알려진 한계** — 재생성은 요청이 있어야 트리거된다. 9/8 10:00 이후 첫 방문자는 최대 10분 stale 화면을 볼 수 있다.

## 작업 2 — 정정 감시 상태 갱신, 9/2 기재정정 반영 (2026-09-07)

**결정과 근거** — DART에는 9호 신고서가 8/6 원본·8/14 정정·9/2 정정 세 판인데, 화면의 정정 이력은 8/29 확인 파일(8/14 정정 1건)에 머물러 9/2 정정(20260902000022)이 없었다. `npm run watch:refresh`(DART 공시검색만 호출, 이력제 미호출)로 한우 1~9호 감시 파일을 재생성해 커밋했다. 9/2 정정은 폐사율·이해상충 위험 문안 변경이며 청약 일정·두수·금액은 불변(`docs/research/기획서-정비-2026-09-05/02-제도-시장-변동-갱신.md` §4-1)이라 활성 접수번호(8/14)와 공개 리포트는 유지했다.

**트레이드오프** — 활성 접수번호를 9/2 판으로 올리려면 원문 수집·필링 코퍼스 감사·리포트 재발행·리플레이 갱신이 연쇄되어 마감 직전 위험이 크다. 화면은 "정정 접수됨, 재대조 미실행" 상태를 정직하게 표시한다.

**검증 영향** — 익명화 게이트 테스트가 `data/public/watch/`를 스캔한다(접수번호·보고서명만 포함). 크론 `/api/cron/monitor`(월·목 09:00 KST)는 같은 계보를 DB 원장에 기록하지만 화면은 커밋 파일만 읽으므로 자동 반영이 없다는 사실을 재확인했다.

**알려진 한계** — 라이브 재검증 API와 리플레이 화면은 여전히 8/14 판 기준이다. 청약 진행 중 DART 신규 공시는 9/23 배정공고 전까지 없고, 청약 경쟁률은 플랫폼 화면 전용(수집 금지 R-INV-11)이라 심사 기간에 화면이 바뀌는 것은 청약 단계 배지와 추가 정정뿐이다.

## 작업 3 — 홈 검색의 legacy 부동산 공모 링크 404 (2026-09-07)

**결정과 근거** — `global-search.ts`의 published 매핑이 `OFFERS` 전체를 `categoryId:"cattle"`로 고정하고 `productHref`를 무조건 붙여, 부동산 A(`real-estate-a`)가 "부동산 A"·"한우 공모" 질의에서 `/real-estate/products/real-estate-a`로 노출됐다. 그 경로는 승인 시나리오 13건만 정적 생성하고 `dynamicParams=false`라 404다(로컬 프로덕션 빌드 실측). 기존 `routes.test.ts`가 "부동산" 질의에 legacy 3건이 나오지 않아야 한다고 단정하고 있어, 카테고리를 바로잡는 대신 published 매핑에서 `assetKind !== "livestock"`을 제외했다(부동산 상품은 시나리오 블록이 따로 공급).

**트레이드오프** — legacy 부동산 공모는 검색에서 사라진다. 상세 페이지가 없어 애초에 도달 불가였으므로 잃는 기능은 없다.

**검증 영향** — `global-search-links.test.ts` 신설: legacy 부동산 id 부재, published-offer href가 정적 생성 id 집합과 일치. 기존 `routes.test.ts` 부동산 단정과 정합.

**알려진 한계** — `/offers/common/[categoryId]/[productId]`는 공개 승인 상품 0건이라 정적 경로가 없고 `commonProductHref` 결과는 전부 404다. 현재 검색 결과에 common 항목이 나오지 않아 노출은 없으나 승인 상품이 생기면 같은 구조의 문제가 재발한다.

## 작업 4 — vitest 기본 타임아웃 20초 (2026-09-07)

**결정과 근거** — 축산 질병 코퍼스 결합(0c3da40~d252476) 이후 필링 코퍼스 계획·다중 공시 런타임 테스트가 병렬 실행 부하에서 5초 기본 타임아웃을 넘겨 전체 실행에서 10건이 실패했다(단독 실행 4.5초 통과). CI 러너는 로컬보다 느리므로 `vitest.config.ts`에 `testTimeout: 20_000`을 두었다. 코드 경로 자체는 프로덕션 빌드 실측에서 검색 0.2초·근거 질의 0.5초 이내라 성능 회귀는 아니다.

**트레이드오프** — 느려진 테스트를 드러내는 신호가 약해진다. 대안인 코퍼스 로딩 캐시·테스트 픽스처 축소는 마감 후 과제로 미룬다.

**검증 영향** — 전체 스위트가 병렬 실행에서도 그린이어야 한다.

**알려진 한계** — 타임아웃 상향은 원인 제거가 아니다.
