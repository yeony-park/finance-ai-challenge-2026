# Stream 7 — 사용자 편의성 드릴다운: 카카오페이 보험진단 vs 약관 자동 로드 UX

> 2026-08-07 리서치(2개 병렬 에이전트). 질문: "카카오페이 보험진단을 편의성에서 따라잡을 수 있는가?"
> 결론 선행: **정면 승부는 불가능하지만 불필요하다. 조항 검증 영역에서는 카카오페이의 편의성 우위(마이데이터 제로 입력)가 이전되지 않는다 — 마이데이터에 약관 원문이 없기 때문이다.**

## Executive Summary

카카오페이의 편의성은 실재한다: 마이데이터 연동 한 번으로 신용정보원 가입내역+건보공단 검진 데이터가 자동 유입되는 제로 입력 구조, 카톡 내장 진입, 2,000만 가입자. 그러나 ① 마이데이터 보험 API에는 **약관 원문이 없다**(API 규격 직접 확인 — 계약·담보 구조화 데이터뿐). 약관 원문의 유일한 합법·무인증 소스는 **보험사 상품공시실**이며, 이는 카카오페이든 우리든 동일 조건이다. ② 카카오페이의 약관 학습은 모델 내부 지식일 뿐, **사용자가 조항 원문을 근거로 제시받는 UX가 없다**. 따라서 조항 검증이라는 우리 경기장에서 편의성 격차는 "약관 구해오기 마찰"로 좁혀지고, 이는 **프리로드 코퍼스 + 상품명 퍼지 매칭 + 업로드 폴백의 3층 입력 구조**로 5주 내 해소 가능하다(실현 가능성: 중간~높음).

## 1. 카카오페이 '보험진단'의 실체 (2026.8 기준)

단일 서비스가 아니라 3개 층위의 조합: **페이아이 챗봇 'AI로 내 건강 관리하기'**(2025.6 정식, sLLM에 공단 검진 데이터+보험약관 학습) + **'내 건강 분석'**(2025.12, 검진 10년치 9개 카테고리·또래 100명 중 순위) + **'내 보험 진단하기'**(2021~, 비AI 마이데이터 리포트). 2026.8.4 'AI코치' 베타는 소비 분석 중심으로 보험진단 미포함. ([머니투데이 CTO 인터뷰](https://www.mt.co.kr/finance/2025/06/11/2025060914225411529), [ZDNet](https://zdnet.co.kr/view/?no=20260804171414), [보험저널](https://www.insjournal.co.kr/news/articleView.html?idxno=27019))

### 강점 (따라잡을 수 없고, 따라잡을 필요 없는 것)
- 제로 입력: 마이데이터 연동 1회 → 가입내역+검진 데이터 자동. 업로드·수기 입력 전무
- 카톡 진입점 + 마이데이터 가입자 2,000만 풀
- 또래 상대 비교 UX(해석 부담 최소화), 건강 데이터 × 보험 데이터 개인화
- 혁신금융서비스 지정, 자체 GPU·오픈웨이트(망분리 대응)

### 한계 (우리 경기장)
1. **약관 원문·조항 단위 근거 제시 없음** — 약관은 학습 재료일 뿐. "내 약관 제15조에 따르면…" 식 인용 UX 미확인. 상품 설명 수준 챗봇 답변 [추론, 전 자료 교차]
2. **이해상충 구조** — 진단 주체 = 판매 주체 그룹(자회사 KP보험서비스 GA + 카카오페이손보). "보장 부족" 판정에 구조적 인센티브 ([플래텀](https://platum.kr/archives/189265))
3. 심층 해석은 결국 "전문가 상담 연결"(인간 GA)로 이탈 — AI가 끝까지 답하지 못함
4. 검진 데이터 없는 사용자(사회초년생 등) 사각지대, 모바일 전용
5. 규제(권유·적합성)로 답변 범위를 의도적으로 제한, 단계 개방 중 ([ZDNet](https://zdnet.co.kr/view/?no=20260804171414))
6. 출시 1년이 지나도록 자발적 체험기·리뷰 희소 — 실사용 만족도 미검증 [검색 한계 병기: 네이버 블로그/카페 인덱스 제한]

## 2. 약관 원문 확보 경로 전수 조사

| 경로 | 판정 | 핵심 근거 |
|---|---|---|
| 보험사 상품공시실 | **가능** | 전 보험사 공시 의무(시행세칙), 로그인 불요, 판매중지 상품 포함. 삼성화재는 정적 PDF URL(`…/publication/pdf/{상품코드}_{버전}_{시행일자}_file1.pdf`, robots Allow, curl 200 확인), DB손보는 AJAX JSON(상품명·판매개시일·약관 파일명 필드). 단 삼성생명·메리츠는 SPA(헤드리스 필요), 한화는 봇 차단 — **보험사별 어댑터 필요** |
| 협회 비교공시 | 불가~조건부 | 약관 PDF 링크 없음(보험료·보장 비교만). 생보협회 robots.txt는 네이버·다음 외 전 봇 Disallow. 상품명 표준 목록 메타데이터로만 유용 |
| 마이데이터 API | **불가(확정)** | [보험 업권 API 규격](https://developers.mydatakorea.org/mdtb/apg/mac/bas/FSAG0403?id=3) 직접 확인 — 계약·특약·담보·납입 구조화 데이터뿐, **약관 원문 API 없음**. 스크래핑은 2022.1부터 전면 금지, 허가제 |
| 내보험찾아줌/다보여 | 조건부 | 본인인증 후 보험사명·상품명·증권번호 확인 가능. 약관 연결·공개 API 없음 → **"정확한 상품명 확인용 수동 브릿지"**로 활용 |
| 소비자 실태 | — | 약관 분실이 일반적, 손해사정사·금융권 가이드가 "공시실에서 검색하라"고 안내 — **공시실 검색이 이미 사실상 표준 경로**. 우리 서비스의 자동화가 실제 마찰을 정조준 |

### 전략적 함의 (핵심)
**마이데이터의 편의성 우위는 "가입 상품 식별"까지만 미치고 "약관 원문"에는 미치지 못한다.** 카카오페이가 조항 검증 기능을 만들려 해도 약관은 공시실에서 수집해야 하며, 이 지점에서는 우리와 동일 선상이다. 즉 조항 검증 영역의 편의성 경쟁은 "누가 공시실 약관을 더 매끄럽게 연결하느냐"의 싸움이고, 이는 5주 MVP로 선점 가능한 영역이다.

## 3. MVP 입력 UX — 3층 구조 (권장)

1. **프리로드 코퍼스 선택형 (기본 플로우)** — 주요 6개사(삼성생명·삼성화재·한화·교보·DB·메리츠) × 인기 상품군(암·실손·종신) 약관을 사전 수집·색인. 사용자는 "보험사 → 상품군 → 상품명(판매시기)" 3단 선택. 업로드 없이 3탭이면 분석 시작 — **데모 신뢰성 100%, 심사 기간 무중단에도 유리**
2. **상품명 검색 자동 매칭 (차별화 데모)** — 내보험찾아줌에서 확인한 상품명을 자유 입력 → 색인에 퍼지 매칭(임베딩+판매시기 필터). 크롤링 쉬운 보험사(삼성화재·DB)는 온디맨드 수집. "약관을 찾아드립니다" 경험
3. **PDF 업로드 폴백 (안전망)** — 미커버 보험사·매칭 실패 시. 어떤 경우에도 막히지 않음

장애물: 소비자 통칭("삼성 암보험")과 공시 정식명("무배당 삼성화재 건강보험 마이헬스파트너(2404.1)") 불일치 + 판매시기별 개정판 다수 → 삼성화재 URL의 시행일자, DB의 판매개시일 필드가 역으로 매칭 키가 됨. 가입연월 입력으로 보정.

## 4. 기획서 반영 포인트

1. **편의성 비교표를 정면으로 넣되 축을 바꿀 것**: "연동 편의성"(카카오페이 승) vs "조항 근거 제시·중립성·약관 접근"(우리 승). 카카오페이의 이해상충(진단=판매 주체)과 조항 인용 부재를 명시하면 "대형 플랫폼이 하면 어떡하나" 질문에 대한 답이 됨 — 판매 채널은 자사 유통 상품의 불리조항을 표시할 유인이 구조적으로 없음.
2. **"3탭 분석 시작" 지표화**: 프리로드 플로우 기준 "업로드 없이 3번 선택으로 분석"을 편의성 정량 지표로 제시.
3. **시니어·초보자 타깃과 연결**: 공시실 검색은 시니어에게 높은 장벽 — 자동 매칭이 대회의 "금융소비자 특성 고려" 요건과 직결.
4. **수집 파이프라인 범위 명시**: 6개사 어댑터 + robots 준수(공시자료, 삼성화재 Allow 확인) — 기능명세서에 커버리지 한계 정직 고지.

## Methodology

2개 병렬 에이전트: ① 카카오페이 서비스 계보·UX·수익 구조(도구 호출 30회, 보도·공식 페이지 교차), ② 약관 확보 경로(37회, 보험사 공시실 curl 직접 확인·마이데이터 API 규격 원문·robots.txt 검증). 검색 한계(네이버 블로그 인덱스 제한)는 본문에 병기. 실화면 검증은 팀원 직접 체험(카톡 페이홈 > 전체 > 편의 > 'AI로 내 건강 관리하기') 권장.
