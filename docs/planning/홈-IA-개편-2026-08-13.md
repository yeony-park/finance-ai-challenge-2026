## 1. 배경 · 진단

현행 홈은 **단일 리포트 홍보 페이지**다. `page.tsx`가 `FEATURED_OFFER_ID` 한 건만 읽어 Hero → Reports(1건) → Method → Watch → Verdict의 세로 서사로 흘린다.

| 증상 | 코드 근거 |
|---|---|
| 집계도 목록도 없다 | `loadLatestReport(FEATURED_OFFER_ID)` — 홈이 리포트를 1건만 읽는다 |
| 확장 불가 | 축 B 자리가 하드코딩된 "준비 중" 카드(`ReportsSection.tsx` 62~76행)라 공모가 늘어도 카드가 늘지 않는다 |
| 한눈에 안 보인다 | 판정 수치는 Hero 카드와 Reports 카드에 중복 노출되고, 그 사이를 설명 문단이 메운다 |
| 자기보고형 문장 중심 | "…합니다 / …남깁니다 / …적지 않습니다" — 주어가 전부 서비스다 |

가장 큰 문제는 마지막이다. 심사자가 보는 것이 **공모의 상태**가 아니라 **서비스의 자기소개**다. 공모 2건이 붙는 S2 시점에 이 구조는 그대로 무너진다.

## 2. 설계 원칙 — 자기보고형 금지

**화면 모든 문장의 주어는 서비스가 아니라 공모·자산이다.**

| 금지 (자기보고형) | 준수 (공모가 주어) |
|---|---|
| 우리는 37건을 대조해 1건 불일치를 발견했습니다 | 이 공모의 개체 37두 중 1두가 국가 원장에서 확인되지 않습니다 |
| 발행사가 적어 낸 주장을 국가 공공데이터와 자동으로 대조합니다 | 신고서에 적힌 개체 37두가 국가 이력 원장에 등록돼 있습니다 |
| 정정신고서가 접수되면 같은 파이프라인으로 다시 대조합니다 | 이 공모는 정정 2회 접수 · 최근 재대조 8/12 01:40 |
| 아직 공개되지 않은 축은 비워 둡니다 — 채워 넣지 않습니다 | (문장을 쓰지 않는다. 카드가 없으면 없는 것이다) |
| 판정하되 단정하지 않는 독립 검증 레이어입니다 | (→ `/methodology`) |
| 확인 비용 때문에 대다수는 확인을 포기합니다 | (→ 기획서 · `/methodology`) |

> 준수 예문의 37은 **개체 수(두)**이지 claim 항목 수가 아니다. `verdict-section.ts`의 `summary.total`(claim 수)과 혼동하지 말 것.

### 예외 4종 — 서비스가 주어인 문장이 허용되는 유일한 자리

| # | 예외 | 위치 |
|---|---|---|
| ① | 한 줄 정의 **1문장** | 홈 Hero (아래 표준문) |
| ② | 법적 고지 | 푸터 — "본 서비스는 투자 권유·자문이 아닙니다" 등 |
| ③ | 상태·오류 화면 | `src/app/not-found.tsx` · `src/app/error.tsx` (404·error) |
| ④ | 조작 마이크로카피 | 버튼·토글 힌트 등 UI 조작 안내 |

예외 자리에서도 **서비스 성과·기능 자랑은 불가** — 서비스의 성격·한계 고지만 가능하다.

**정의 표준문**: 「증권신고서를 국가 공공데이터와 대조합니다」 — 이 1문장이 표준이다. `service.ts`의 3절 `SERVICE_DEFINITION`은 S1에서 이 표준문으로 축소한다(§4.7). 메타데이터·OG description은 화면 문장이 아니므로 이 원칙의 적용 대상 외다.

**판정 명칭 정책**: 화면에 노출하는 판정 명칭은 **「일치 / 원장 미확인 / 대조 불가」** 3종만 쓴다. "불일치"는 내부·문서용 용어로만 사용하고 화면에 내보내지 않는다.

### 담당 분리

| 내용 | 담당 |
|---|---|
| 공모의 현재 상태 · 판정 · 일정 | `/` · `/offers/[id]` |
| 판정 기준 · 3값 정의 · 한계 · 데이터 출처 | `/methodology` |
| 설득 논증(병목 실측), 실적 수치(정정 65% · 공모당 2.4회) | `/methodology` + 기획서 |
| 투자 권유 아님 고지 | 푸터(전 페이지 상시 노출, 이미 구현됨) |

> 심사자 어필은 설명문이 아니라 **"심사자가 진짜 투자자처럼 써 보게 되는 화면"**으로 달성한다.
> 판단 근거: 청약 D-day가 붙은 목록은 읽는 대상이 아니라 **고르는 대상**이다.

### 3.3 커버리지 표기

분모는 2026년 투자계약증권 공모 전수, 분자는 `PUBLISHED_OFFER_IDS.length`. 목록이 전수가 아니라는 사실을 숨기지 않는다. 분모는 상수로 두고 집계 출처를 주석으로 남긴다(현행 `WatchSection`의 `statSource` 처리와 같은 방식).

**문장 주어 규정**: 커버리지 문장의 주어는 공모다 — 「2026년 투자계약증권 공모 8건 중 2건이 국가 공공데이터 대조를 거쳤습니다」가 표준이다. "…의 대조 결과가 있습니다"처럼 서비스 산출물이 주어가 되는 문형은 쓰지 않는다.

### 4.2 데이터 계층 — 신규 필요분

**핵심 제약: 청약 일정은 리포트 어디에도 없다.**

`ReportSnapshot.document`는 `{ offerId, rcpNo, submittedOn }`뿐이고(`report/snapshot.ts` 14~18행), `DemoView`에도 청약 관련 필드가 없다. 목록이 요구하는 청약 시작/종료·D-day는 **리포트에서 파생 불가**하므로 별도 레지스트리를 만든다.

**신규** `src/components/site/offers.ts` — 공모 레지스트리 (`service.ts`에서 `PUBLISHED_OFFER_IDS` 이관)

```ts
export interface OfferEntry {
  readonly id: string;           // 라우트 키 = data/public/{id}
  readonly title: string;        // 목록·리포트 공통 명칭
  readonly assetLabel: string;   // "가축" | "부동산"
  readonly subscription: {       // 청약 일정 — 신고서 본문에서 옮겨 적은 값
    readonly opensAt: string;    // ISO
    readonly closesAt: string;
  };
}
```

> 왜 상수 파일인가 — 청약 일정은 신고서 본문 값이지 대조 산출물이 아니다. 엔진이 파싱해 리포트에 싣기 전까지는 화면 상수로 두고, 파서가 일정을 뽑게 되면(S1 파서 일반화) 레지스트리를 리포트 파생값으로 바꾼다. 이때 바뀌는 파일은 이 하나다.

**신규** `src/lib/verify/report/view-model/offer-card.ts` — 목록 카드 뷰 모델

| 필드 | 출처 | 상태 |
|---|---|---|
| `title` / `assetLabel` | 레지스트리 | 신규 |
| `schedule.phase` (`open`\|`closed`) | 레지스트리 `closesAt` vs 기준 시각 | 신규 |
| `schedule.label` / `schedule.dday` | 레지스트리 + 기준 시각 | 신규 |
| `verdictLine` (공모가 주어인 한 문장) | `ctx.matched` / `mismatched` / `headCount` | **문장만 신규**, 수치는 기존 |
| `tallies` | `buildVerdictSection` 결과 재사용 | 기존 |
| `lastVerifiedAt` | `ctx.generatedAt` | 기존 |
| `amendment.count` | `LoadedReport.versionCount` | 기존이나 **`DemoView`로 노출 안 됨** |
| `href` | `/offers/${id}` | 기존 |

`versionCount`는 `loadLatestReport`가 돌려주고 `ReportContext`가 들고 있지만 `DemoView`에는 뚫려 있지 않다. 카드가 "정정 n회 접수"를 쓰려면 `offer-card.ts`가 `ReportContext`에서 직접 읽어야 한다(`toDemoView`와 형제 함수로 두고 `buildReportContext`를 공유).

`D-day`는 **빌드 시각 기준으로 굳는다**. 정적 프리렌더라 배포 시점에 고정되므로, 기준 시각을 인자로 받는 순수 함수로 만들고(테스트 가능) 배포 시점에 갱신되게 한다. cron 재검증은 S2 후반 도입 예정이라 그 전까지는 수동 재배포가 갱신 수단이다(§6-6).

**ReportFoot 방침**: 인라인 링크 도입 후 `report/ReportFoot.tsx`는 고지 문장 수준으로 축소한다 — 판정·방법 설명은 인라인 링크와 `/methodology`가 담당한다.

## 6. 착수 전 확인된 난점

1. **`offerTitle`이 공모별로 유일하지 않다.** `view-model/context.ts` 72행이 `공모 A · ${breed} 사육 투자계약증권`으로 제목을 만든다. 접두사 `공모 A`가 고정이라 2건을 나란히 놓으면 **둘 다 "공모 A"**가 된다. 제목은 레지스트리로 옮긴다.

2. **`buildOfferSection` / `buildVerdictSection`이 축산 전용이다.** `개체 ${headCount}두`, `개체 N두 전수 대조 · 국가 원장`(`verdict-section.ts` 22·28행) — 부동산 리포트에 그대로 쓰면 `0두`가 찍힌다. 카드의 판정 요약 문장은 **자산군별 분기**가 필요하다. 축 A는 개체 수 기준, 축 B는 비교군·백분위 기준.

3. **`context.ts`의 `breed` 파생이 축산 claim에 묶여 있다.** `livestock_breed` claim이 없으면 `"기초자산"`으로 떨어진다. 부동산 리포트는 이 경로를 타면 안 된다.

4. **claim 스키마가 축산 6종으로 닫혀 있다.** `snapshot.ts` 21~30행 `kind` enum에 부동산 항목이 없다. 축 B 리포트가 `data/public/`에 생기려면 엔진 스키마 확장이 선행돼야 하고, **그 전에는 홈 목록이 2건이 될 수 없다**. 홈 개편을 S2 초에 두되 축 B 어댑터 뒤에 붙인 이유다.

5. **`landing.module.css`가 639줄로 섹션별 구분 없이 이어진다.** 3개 섹션을 지우면서 어떤 클래스가 살아남는지 확인이 필요하다 — `reportCard` 계열과 `toneGood/Warn/Unk`, `statusPill`은 카드로 승계되고 나머지 대부분은 삭제 대상이다.

6. **D-day는 정적 값이다.** 빌드 시각에 굳으므로 재배포 없이는 갱신되지 않는다. cron은 S2 후반 도입 예정 — 도입 전까지는 **수동 재배포로 갱신**한다. "D-14"가 며칠 묵을 수 있다는 점은 인지하고 있어야 하며, **9/10 16:00 청약 종료 직후 1회 재배포(프리즈 예외)**로 심사 기간 중 그룹 분류·D-day 정확성을 유지한다. D-day 계산은 기준 시각을 인자로 받는 순수 함수로 분리해 테스트 가능하게 둔다.

7. **`VerdictSection`의 `VERDICT_TERMS` export는 어디에서도 쓰이지 않는다.** `SiteFooter`가 자체 배열을 들고 있어 파일 삭제 시 연쇄 수정이 없다 — 폐기 비용 0.
